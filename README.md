# Классификация кредитного рейтинга: цена утечки данных

Задача: по банковским данным клиента предсказать кредитный рейтинг (`Poor`, `Standard`, `Good`). Датасет [Credit Score Classification](https://www.kaggle.com/datasets/parisrohan/credit-score-classification), 100 тысяч строк, мультиклассовая классификация с дисбалансом 53% / 29% / 18%.

Первый прогон дал accuracy 0,77, что совпадает с публичными решениями по этому датасету (там обычно фигурирует цифра около 80%). Разобравшись в структуре данных, я понял, что эта цифра завышена утечкой, и дальше проект был про то, чтобы её измерить и убрать.

**Стек:** Python, pandas, NumPy, scikit-learn (Pipeline, ColumnTransformer, GroupShuffleSplit, HistGradientBoostingClassifier, LogisticRegression, permutation_importance), matplotlib, Jupyter.

## Что не так с публичными решениями

Перед тем как писать свой пайплайн, я разобрал десяток топовых ноутбуков по этому датасету. В большинстве из них повторяются две методологические ошибки, и обе завышают итоговую метрику.

**Первая: игнорирование панельной структуры данных.** Строк 100 тысяч, а уникальных клиентов 12,5 тысяч: ровно по восемь строк на человека, по одной на месяц наблюдения. Возраст, профессия, доход и большая часть кредитной истории между месяцами не меняются. При случайном `train_test_split` по строкам один и тот же клиент попадает и в обучение, и в тест, и модель на тесте узнаёт людей, которых уже видела.

Долю таких клиентов можно оценить заранее. При доле теста $\alpha$ все восемь строк клиента попадут в одну часть с вероятностью $P = \alpha^8 + (1-\alpha)^8$
При $\alpha = 0{,}25$ это около $0{,}100$, то есть примерно 90% клиентов размазаны между выборками. На данных получилось 11 299 из 12 500, то есть 90,4%: расчёт сошёлся с фактом.

**Вторая: препроцессинг до сплита.** `MinMaxScaler`, `PCA` и заполнение пропусков обычно применяются ко всей выборке сразу, то есть статистики теста протекают в обучение. Это вторая утечка поверх первой.

Коварство обеих в том, что изнутри эксперимента они не видны: отложенная выборка выглядит нормально, кросс-валидация даёт стабильные цифры. Найти их можно только через анализ структуры данных.

## EDA и подготовка данных

Данные в датасете намеренно испорчены: числа записаны строками (`_23`, `28_`), встречаются заглушки (`!@9#%8`, `_______`), стаж кредитной истории лежит текстом вида `"22 Years and 1 Months"`.

Дисбаланс 53% / 29% / 18% сразу показывает, что одной accuracy для оценки будет мало.

Здесь видны возраст 8698 лет, 1798 банковских счетов, пять тысяч просроченных платежей. Это не выбросы, а битые записи, всего 28 766 штук.

**Решение: помечать как пропуски, а не удалять строки.** Удалять нельзя по двум причинам. Во-первых, у клиента восемь строк, и выбросив три, получаешь рваную историю. Во-вторых, последовательная фильтрация по десятку колонок смещает распределение целевой переменной. В итоге строк потеряно ноль.

## Корректный пайплайн

Разбиение по `Customer_ID` через `GroupShuffleSplit`, причём до любых преобразований, которые считают что-то по данным. Медианы, моды, масштаб и набор категорий обучаются внутри `Pipeline` строго на train, one-hot кодирование через `OneHotEncoder`. Пропуски заполняются значением того же клиента за другой месяц.

Метрики: accuracy, macro-F1, ROC-AUC (one-vs-rest) и

$$Gini = 2 \cdot AUC - 1$$

Baseline (константный прогноз мажоритарного класса) даёт accuracy 0,5312, и именно это, а не ноль, есть настоящая точка отсчёта для "80%" из публичных решений.

## Выводы

Честная модель на этих данных даёт Gini 0,7147, а не 0,8161. Разница в 12,4% это цена ошибки, которая воспроизводится в большинстве публичных решений и которую невозможно обнаружить по метрикам валидации. Сплит обязан быть групповым, иначе оценка качества модели систематически завышена, и на проде она покажет заметно худший результат, чем на валидации.
